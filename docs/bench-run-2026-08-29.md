# First bench run — 29 August 2026

Acer, Ubuntu live (release codename `resolute`), tester ADK. 13 records.
Raw setup output in `../raw/2026-08-29-setup-terminal-output.txt`.

## What it proved

**The Acer boots from USB.** The item flagged as blocking everything since the first
review. Closed.

**The protocol works end to end.** Setup, detect, capture, record, download. No step
was impossible.

**Median 2 minutes per device once running.** The "twenty minutes" figure in
`bench-kit/protocol.md` was a guess about the whole first-time experience, not per
device. Corrected: about 90 minutes the first time including making sticks and booting,
2 to 5 minutes per device after that.

## The finding that matters

**The v1 classifier could not tell an Android phone from a camera, and got it wrong
nine times out of thirteen.**

USB interface class 0x06 covers both PTP (cameras) and MTP (phones in file-transfer
mode). v1 mapped 0x06 straight to `ptp_camera`. Result:

- Samsung A5, captured in 4 USB modes → `ptp_camera` ×3 and `unknown` ×1
- Nothing Phone 1, captured in 5 USB modes → `ptp_camera` ×5

Two real Android phones, nine captures, **zero** classified as Android. `coverage.py`
reported 0 live positives from a session that physically contained two.

This is the /e/OS codename problem in a different costume, and it is worse: that one
produced a false negative with a confusing message. This one would hand a verifier the
wrong device class entirely, which is a false-safe pathway. It belongs in Q6 alongside
the codename case.

**Classifier v2** (`bench-kit/scripts/01-detect.sh`) resolves class 0x06 using the
interface string first (`MTP` is explicit when present), then the vendor ID against a
phone-vendor list and a camera-vendor list, falling back to `ptp_or_mtp` at low
confidence when neither matches. Replayed against these 13 records it corrects all nine
and leaves the four correct ones alone.

**The second-order finding: no fingerprints.** Even correctly classified as phones, none
of the nine captures carries a model, chipset, partition scheme or bootloader state,
because USB debugging was off. `01-detect.sh` now detects a phone vendor and tells the
tester to enable debugging and capture again, and `START-HERE.html` puts that step
*before* the capture rather than after.

## Network

`00-setup.sh` needs internet. It installs `adb` and `fastboot` from the Ubuntu archive,
about 1.5 MB. Nothing else does: detection, fingerprinting, the console page, record
building and download are all offline. Now stated explicitly in the guide.

## Mount paths

The kit mounted at `/run/media/ubuntu/BENCH`, not `/media/$USER/BENCH` as the guide
assumed. Both are used depending on release. The guide now tells testers to right-click
the folder and choose "Open in Terminal" rather than typing a path at all.
