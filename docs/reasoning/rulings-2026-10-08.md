# Rulings of 8 October 2026

*Five decisions made by Ranaji after the round 2 review, the fourth revised the same day,
(`Claude outputs/flashguard-round2-review-2026-10-08.md`, outside the repo). Each is held by a
test that fails without it: `tests/test_rulings_2026_10_08.py`, the derivation fixtures in
`tests/android/` and the console tests in `tests/run-console-logic.js`.*

## 1. The bench kit is unfrozen, and reads twelve more properties

The freeze held from 29 August. Round 2 showed questions the existing allowlist cannot
answer, so the kit now also reads:

| Property | Answers |
|---|---|
| `ro.product.first_api_level`, `ro.board.first_api_level` | Launch era. Lock state split cleanly at Android 8 on the *running* firmware; this tells running from launch apart. |
| `ro.treble.enabled`, `ro.boot.dynamic_partitions` | Layout evidence, toward a positive signal for a single layout. Recorded, not yet derived into `partition_scheme`. |
| `ro.build.type`, `ro.build.tags` | Firmware origin (ruling 3). Read from the fingerprint when absent. |
| `ro.build.product`, `ro.product.name` | Codename aliases on stock firmware (`OP5958L1` is LineageOS `larry`). |
| `ro.product.vendor.device`, `ro.product.vendor.model` | Identity from the vendor partition, which often survives a custom ROM. |
| `ro.boot.hardware.sku` | Motorola's XT model code; `ro.product.model` carries a marketing name. |
| `ro.lineage.device` | The codename a LineageOS build was made for. |

Each was checked before adding: none carries a serial, IMEI, MAC or account identifier.
The kit asks the tester nothing new. Two console defects were fixed with them: a phone's descriptor no longer gets
`#!expect=adb` unless the tester said USB debugging is on, and an interface the browser does
not recognise is `unknown`, never the class of the category the tester picked.

*Added 17 October, at Ranaji's request after round 3.* The tester's "debugging is on" answer
was still taken as the assertion when the port said otherwise: an Xperia XA2 in tethering mode
and an Edge 30 Ultra showing only a vendor interface were stamped `adb` and blocked the commit.
Now a phone's descriptor asserts `adb` only when the tester said debugging is on **and** that
read shows the ADB interface (255/66/1). When the two disagree, the descriptor carries a
`#!note` saying so and asserts nothing. A device the browser did not read is `unknown`, never
its category. The tester is warned before the terminal step when the read showed no debugging
connection. Held by `tests/run-console-logic.js`. Kit package `2026-10-17`.

## 2. Tier A is reported per storage layout

No phone without A/B partitions reports a property that says so (13 of 13 by 7 October), so
"all seven fields" could only be met by A/B phones. `coverage.py` now counts a phone complete
when it carries every field its layout can report: seven for A/B, virtual A/B or an explicit
single; the other six when the layout is not reported. The rows are printed separately, and
the report says that the verifier still abstains on every recipe for the second group.

## 3. Custom firmware is in scope

`derive.sh` reports `firmware_origin`: `custom` on positive evidence (`ro.lineage.device`,
halium, a lineage_/aosp_ build, userdebug or eng, test-keys, or a fingerprint whose Android
version differs from the running one), `stock` only for a user build with release-keys and no
custom marker, `unknown` otherwise. Unlocked is not custom. `merge.py` backfills the field for
earlier records from their own fingerprint, through `derive.sh`, and marks it as backfilled.

In the verifier, on custom firmware:
- identity a ROM wrote can **confirm** a recipe (product, vendor or lineage device code) but
  never **condemn** one: a mismatch is `identity-custom-firmware`, an abstention, not `unsafe`;
- the software model string is not used; only `hardware_sku`, `vendor_model` or the label;
- a stock-firmware prerequisite (`android_version`, `sdk`, `security_patch`) abstains with
  `firmware-version-custom-rom`, because the phone is not running the vendor's firmware.

Not covered: a stock phone whose codename differs from upstream (`OP5958L1` vs `larry`) still
returns `unsafe` on `device-mismatch`. That is a separate decision, not taken here.

`merge.py` no longer joins two records whose chipsets differ: two Ubuntu Touch Xiaomis
(sdm660 and mt6768) had been merged into one device.

## 4. The verifier settles the model from sources, and asks only when they cannot

*Revised the same afternoon. A first version asked every tester to check the model printed on
the phone during capture. That added friction for testers and, later, for every user, so it
was removed: capture asks nothing about the model.*

A recipe carries, under `target`, every upstream entry that relates to its device, isolated
from the clones by `tools/model-sources.py`:
- `models_sources`: the entries the recipe rests on, each with the model codes it lists (an
  empty list means it names the device but no codes);
- `competing_sources`: entries sharing the codename that are a different device, such as
  another LineageOS variant (6T and 6T T-Mobile) or one listing other codes (Nord CE 3 Lite
  and Nord N30 share `larry`).

Only sources on a domain in `data/vocabulary.json` (`model_source_domains`) count as credible.
The verifier then works through the confusion in this order:

| The phone reports | Credible sources | Result |
|---|---|---|
| A model code a credible source lists | list codes | settled, no one asked (`match-product_model`) |
| A different device code, but a listed model code | list codes | settled by the model (`match-device-by-model`): stock firmware's internal names such as `OP5958L1` |
| A model the sources do not list | list codes | `unsafe` on stock (a sibling such as the N30), abstain on custom firmware |
| A model *name* where the sources list codes | list codes, and name the device | ask (`model-needs-confirmation`): Motorola's marketing name; `ro.boot.hardware.sku` usually settles it first |
| Anything | list no codes at all | ask (`model-needs-confirmation`): the OnePlus 6T today |

Asking means the verdict is `cannot-verify` and `evidence.confirmation_request` carries the
models the phone reports, the links of this recipe, the links it cannot tell apart from, and
the question. The answer comes back on the fingerprint as `model_confirmation`
(`human_confirmed` with `model_confirmed_source`, the link the person recognised, or
`human_rejected`). It counts only for a link of this recipe, never overrides a credible list,
and a rejection is never a pass. For phones already in the matrix, `tools/confirm-model.py`
records answers into `data/confirmations.jsonl`, which `merge.py` applies; `--pending` lists
the questions the verifier is asking now. On 8 October there are none: every paired phone's
model is listed by a credible source, and the decided share is unchanged at 25%.

## Addendum, 8 October afternoon

**Credible model sources.** GSMArena and makers' own sites count, alongside the upstream
projects (`model_source_domains` in `data/vocabulary.json`). Community forums on a maker's
domain do not (`model_source_excluded_subdomains`: forum.fairphone.com is not Fairphone
speaking). Sources write codes their own way, so a reported model is compared ignoring case
and spacing, and with the phone's own manufacturer name dropped from the front: the 6T reports
`ONEPLUS A6013`, GSMArena lists `A6013`. Only the phone's own manufacturer name is dropped.

**pmaports had stopped updating.** postmarketOS moved its GitLab from gitlab.com to
gitlab.postmarketos.org in October 2024, so the clone's `origin` on gitlab.com reported "up
to date" at 3 November 2024 indefinitely. The remote now points at
`https://gitlab.postmarketos.org/postmarketOS/pmaports.git`.

## Addendum, 8 October evening: unsettled models are not-ready, pending confirmation

When the sources cannot settle which device configuration a phone is, and nothing else is
missing, the verdict is **not-ready**, with `pending_confirmation: true`. It is never `safe`,
it never hides an `unsafe`, and any other abstention (an unreported layout, say) still makes
it `cannot-verify`. The same logic runs in testing and, later, for a public user right after
the fingerprint is captured. The three pending reasons are `model-needs-confirmation` (no
credible source lists codes, or the phone gives a name where sources list codes),
`model-ambiguous-variant` (the code is listed, but a configuration sharing the codename lists
no codes or the same code), and `device-code-differs`.

`evidence.confirmation_request` now carries:
- `mismatch`: where the sources disagree, field by field (what the phone reports, which
  source lists it for this recipe, which configuration cannot be excluded and why);
- `possible_configs`: every configuration the verifier cannot choose between, each with its
  project, name, link, install method, model codes, and whether it is this recipe's;
- `question`, also set as the remedy on the pending reason.

A pending not-ready is **not counted as decided** in the coverage gate.

Two rules came with it. A recipe for `A/B` accepts a `virtual_A/B` phone, because upstream
records only whether a device has slots; the reverse is still a mismatch. Pairing tries a
recipe on a phone whose model code a recipe source lists, not only on a codename match, so
stock firmware's internal names (`OP5958L1`) reach their recipe.

Three recipes were added for phones the sources settle. Their labels rest on public sources
only; Ranaji has deliberately not confirmed them, because he does not own these phones
(decided 11 October):
`larry.json` (Nord CE 3 Lite: not-ready, locked, settled through CPH2467 although the phone
says OP5958L1), `fajita.json` (OnePlus 6T: not-ready pending confirmation, because the 6T and
the 6T T-Mobile share A6013 per GSMArena and LineageOS lists no codes for either), and
`star2lte.json` (Galaxy S9+: cannot-verify, layout not reported, locked).
