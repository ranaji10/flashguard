# Bench run 2, 29–30 August 2026

*The re-run, after the defects the first run exposed were fixed. Written up 6 September,
which is late: `bench-run-2026-08-29.md` was written at 18:20 on the 29th, before this run
started at 22:24, and for a week it was the only run log while claiming to cover both.*

## What it produced

10 records, 8 physical devices, and the first Android fingerprints the project has ever had.

**The Nothing Phone 1 is the first complete record in the matrix.** All seven verifier
fields, each with its evidence recorded beside it:

    manufacturer         Nothing
    product_model        A063 (Spacewar)
    chipset_family       QTI SM7325          from ro.soc.model
    android_version      15 (sdk 35)
    partition_scheme     virtual_A/B         ro.virtual_ab.enabled=true
    bootloader_state     locked              ro.boot.flash.locked=1
    verified_boot_state  green

**The Samsung A5 gave five of seven, and that is the more interesting record.** It exposes
no partition property and no bootloader property at all. The record says so:

    partition_scheme     unknown
    partition_basis      "no ab_update, no slot_suffix, no virtual_ab --
                          absent is not the same as single"

That is the abstain case, from real hardware, with its reason attached. Under the code as it
stood before this run it would have said `single`, confidently and wrongly.

## The controlled comparison

The A5 had USB debugging on during **both** runs. Same phone, same state, same cable, same
machine. Classifier v2 said `ptp_camera`; v4 says `adb`. One variable moved.

That is the only clean before-and-after in the dataset and it is the strongest piece of
evidence the project has. It belongs in the proposal.

Everything else is not comparable: the Nothing Phone had debugging off in run 1, so its
run-1 records were testing a different condition.

## Four defects, all mine, all caught

| Defect | How it was caught |
|---|---|
| `grep -A2` paired a class from one interface with a protocol from another | A synthetic trap fixture written by asking what else the same mistake could produce |
| Partition scheme inferred as `single` whenever the Android version was readable — an absent property becoming a confident answer, on the field the verifier most depends on | Reading `02-android.sh` before it ran on a device for the first time |
| `declare -A` needs bash 4; macOS ships 3.2 | Ten of fifteen fixtures failed the moment the suite ran on the Mac |
| "Same device, different mode" rebuilt its state from scratch, dropping `device_local_id` and `identity_source` | The merge step reported one Samsung as two devices |

The last one is worth dwelling on: the one path where the device is *certainly* the same
physical object was the one that lost its identity, in the feature added to prevent exactly
that.

## A device class nobody had thought of

`0x04e8:0x6845`, the old Samsung, classified as `unknown`. Opening the descriptor to build a
fixture showed why:

    bInterfaceClass         2 Communications
    bInterfaceSubClass      2 Abstract (modem)
    bInterfaceProtocol      1 AT-commands (v.25ter)

A pre-Android handset with an AT-command modem. The classifier had no case for USB class
`0x02` at all. There is now a `cdc_modem` class and the phone is its test.

**None of the eight synthetic fixtures contained a device class their author did not already
know existed.** That is the argument for real descriptors, in one device.

## Nine real descriptors

Captured with `iSerial` stripped at source, verified line by line before publication, and
committed. Six carry human ground truth via `tests/promote.py`; three are kept as evidence
but refused as assertions.

An abstention cannot be ground truth. Marking `unknown` "correct" means *I agree you cannot
tell*, not *unknown is what this is*, and promoting it would lock the classifier out of ever
improving on that device. The guard is automatic.
