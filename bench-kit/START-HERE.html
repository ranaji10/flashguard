When something goes wrong

Every one of these has actually happened. None of them means the project is broken.

Etcher sits on one percentage and never moves

Usually it is working and simply slow. A cheap USB 2.0 stick writing a 6 GB image can take half an hour and sit on one number for minutes.

Check whether it is actually writing. On a Mac, open Activity Monitor, go to the Disk tab, and watch "Data written/sec". Above zero means wait. Flat zero for three minutes means it is hung.

If it is hung: cancel, quit Etcher, move the stick to a different port directly on the machine rather than through a hub or dock, and start again. If it fails twice, use the other stick. A failing stick costs a few euros; your evening does not.

I cancelled Etcher and now the stick is unreadable or "write protected"

Normal, and recoverable. An Ubuntu image is a hybrid ISO, so Etcher writes a read-only ISO9660 partition plus an EFI partition. Cancel halfway and you are left with a partial version of that. Windows reports two write-protected partitions it cannot format. macOS mounts nothing.

Repair it on a Mac, not in Windows. Windows Disk Management cannot handle ISO9660.

  1. Disk Utility → View → Show All Devices. This matters; you need the physical device, not a volume.
  2. Select the top-level entry for the stick. Check the size first. If it says 250 GB, that is your Mac. Stop.
  3. Erase. Format ExFAT, Scheme Master Boot Record.

If Disk Utility errors, in Terminal use diskutil list external physical — it cannot show your internal drive — then diskutil eraseDisk ExFAT NAME MBRFormat /dev/diskN. Read the disk number twice before pressing Enter.

The cd command says "No such file or directory"

The kit is mounted, the path is just different. Ubuntu mounts removable media in more than one place: /media/<user>/BENCH on some releases, /run/media/<user>/BENCH on others.

Skip pathfinding entirely. In the Files app, open the BENCH stick, go into bench-kit then scripts, right-click in the empty space and choose Open in Terminal. The terminal opens already in the right folder.

Or ask the system: df -h | grep media prints the real mount point. Or look at the address bar of the browser showing this page — everything before START-HERE.html is your path.

A device does not show up at all

In order of how often it is the cause:

  1. The cable. Charge-only cables are extremely common and look identical. Try a different one before anything else.
  2. The port. Directly on the machine, not through a hub, dock or adapter.
  3. The screen is locked. Unlock the phone, then unplug and replug.
  4. The USB mode. Pull down the phone's notification shade after plugging in; many default to charging only. Pick File transfer.
  5. A loose connection. If it appears and then vanishes, hold the cable still and try again.

"Not detected, and here is what I tried" is a valid record. Choose "not detected" and write what you tried.

My phone was identified as a camera

USB class 0x06 covers both cameras using PTP and phones using MTP file transfer, so a phone with USB debugging switched off genuinely does look like a camera at this level. The classifier now uses the vendor ID to tell them apart, but it is a guess either way.

This is the most important thing to get right, and the fix is to enable USB debugging before capturing a phone. Without it you record how the phone presents over USB, which is useful, but you get no model, chipset, partition scheme or bootloader state. See the phone step below.

Reference · why the scripts look awkward

They query an explicit allowlist of device properties one at a time instead of dumping everything. Both adb devices and fastboot getvar all print the device serial, and this dataset is published openly. If you ever see a serial, IMEI, MAC or Android ID in output you are about to record, that is a defect worth reporting, not something to edit out.
